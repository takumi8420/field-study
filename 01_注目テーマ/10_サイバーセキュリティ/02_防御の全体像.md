# 防御の全体像（境界防御からゼロトラストへ、EDR／SIEM／SOC、インシデント対応）

**このノートで分かること**：セキュリティ製品のカタログに並ぶ略語が、
**「どこを守るための道具か」という1枚の地図のどこに置かれるのか**。
そして、守りきれなかったときに何が起きるのか（インシデント対応の流れ）。

> 製品カテゴリごとの市場やベンダーの細かい競争は
> [情報セキュリティ](../../04_情報通信・IT・ネット/14_情報セキュリティ/README.md) 側の担当。
> ここでは**考え方の骨格**に絞る。攻撃側の構造は [01_攻撃側の経済学](01_攻撃側の経済学.md)。

## 1. 結論：守り方の前提が「城壁」から「検問」へ変わった

かつての防御は**境界防御**（ペリメータ・セキュリティ）と呼ばれた。
社内ネットワークを城壁で囲い、**中に入った人・機器は信用する**という設計である。

この前提を壊したものが3つある。

| 壊したもの | 何が起きたか |
| --- | --- |
| クラウド／SaaS | 守るべきデータが**城壁の外**（他社のサーバー）に出た |
| テレワーク | 社員が城壁の外から仕事をするようになった |
| 認証情報の窃取 | 攻撃者が**正規のIDで正面から入ってくる**ので、城壁が意味をなさない |

そこで出てきたのが**ゼロトラスト**。直訳すると「何も信用しない」だが、
実際の意味は「**社内か社外かでは判断せず、アクセスのたびに毎回確かめる**」である。
製品名ではなく設計思想であり、「ゼロトラスト製品を買えば完成」ではない。

```
【境界防御】城壁モデル                    【ゼロトラスト】検問モデル

   インターネット                             インターネット
        │                                          │
   ┏━━━━┿━━━━┓ ← ファイアウォール          ┌──────┴──────┐
   ┃  社内網   ┃                          毎回チェックする関所
   ┃ 中は信用  ┃                          （誰が／どの端末で／
   ┃ サーバー  ┃                            どの状態で／何に）
   ┗━━━━━━━━━┛                              │      │      │
                                           社内DB  SaaS  クラウド
 一度入られたら中は自由に動ける         入った後も、次の一歩ごとに確認
```

> ポイント：ゼロトラストの本質は「**侵入されることを前提に、
> 侵入後の横移動（ラテラルムーブメント）を止める**」こと。入口を強くする話ではない。

## 2. 多層防御：一枚の壁ではなく、何枚もの網

防御は「防ぐ」だけでは足りず、**防ぐ／見つける／対応する／戻す**の4段が要る。
これを縦（レイヤー）と横（時間）の両方で重ねるのが多層防御の考え方。

```
                 防ぐ        見つける      対応する      戻す
              (Protect)     (Detect)      (Respond)   (Recover)
  ───────────────────────────────────────────────────────────
  人・ID     │ MFA/権限最小  │ 異常ログイン │ アカウント停止 │ 再発行
  端末       │ 資産管理/更新 │ EDR          │ 端末の隔離    │ 再構築
  ネットワーク│ FW/セグメント │ NDR/通信監視 │ 通信遮断      │ 経路再設計
  アプリ/SaaS │ 設定の堅牢化  │ CSPM/監査ログ│ 権限剥奪      │ 設定戻し
  データ     │ 暗号化/DLP    │ 持ち出し検知 │ 公開差止め対応 │ バックアップ
  ───────────────────────────────────────────────────────────
                 ↑ 従来ここに偏っていた    ↑ いま投資が動いているのはここ
```

**なぜ右側に投資が移ったか**：侵入を100%防ぐことができないと分かったから。
「破られない壁」より「破られてから止まるまでの時間」を短くするほうが、
被害額（業務停止日数×日商＋情報流出件数）を直接下げる。

## 3. 略語の地図：EDR / SIEM / SOC / XDR / SOAR

セキュリティの略語は、ほぼ全部が**「どこのログを・誰が・どう見るか」**の違いでしかない。

| 略語 | 読み下すと | 実際にやること | 誰が使うか |
| --- | --- | --- | --- |
| **EPP**（アンチウイルス） | 端末の防御 | 既知の悪いファイルをパターンで止める | 自動 |
| **EDR** | 端末の検知と対応 | 端末の**挙動**を記録し、怪しい動きを見つけて隔離する | SOCの担当者 |
| **NDR** | 通信の検知と対応 | ネットワークの通信を見て異常を探す | 同上 |
| **SIEM** | ログの集約と相関分析 | 機器・サーバー・SaaSのログを**1ヶ所に集めて突き合わせる** | 同上 |
| **XDR** | EDR＋NDR＋ログの統合 | 端末・通信・クラウドを横断して1本のストーリーにする | 同上 |
| **SOAR** | 対応の自動化 | 「この検知ならこの手順」を自動実行する | 同上 |
| **SOC** | 監視する組織 | 上記の道具を使って**24時間365日、人が見る**体制 | 自社 or 外部委託（MDR） |
| **CSPM** | クラウド設定の点検 | クラウドの設定ミス（公開されっぱなし等）を探す | インフラ／SOC |
| **IAM / PAM** | ID管理／特権ID管理 | 誰が何にアクセスできるかを管理する。特権は特に厳格に | 情シス |
| **MFA** | 多要素認証 | パスワード＋もう1要素。**最も費用対効果が高い基本策** | 全社員 |

**EDR**＝Endpoint Detection and Response。ウイルス対策ソフト（EPP）との違いは、
EPPが「悪いファイルを止める」のに対し、EDRは「**普通のファイルが普通でない動きをした**」
ことを記録から見つける点にある。攻撃側がOS標準ツールを悪用するようになったので、
「ファイルの善悪」では判定できなくなった、というのが背景。

**SIEM**＝Security Information and Event Management。
ログを集めるだけの箱ではなく、「A機器のこの記録」と「Bサーバーのあの記録」を
**つなげて初めて意味が出る**ことを扱う道具。ログ量に比例して費用がかかるため、
**何を集め、何を捨てるか**が設計の勘所であり、コストの主因にもなる。

> ポイント：**道具を買っても、見る人がいなければ何も起きない**。
> EDRのアラートは毎日大量に出る。SOC（監視する人と手順）とセットでなければ、
> 「警報が鳴っていたのに誰も見ていなかった」という典型的な失敗になる。

## 4. 「見る人」をどう用意するか

自社でSOCを持つのは、24時間3交代×複数名が要るため現実的でない組織が多い。
そこで3つの選択肢が並ぶ。

| 形 | 中身 | 向く組織 | 注意点 |
| --- | --- | --- | --- |
| 自社SOC | 人も道具も内製 | 金融大手、通信、重要インフラ | 人件費が重い。人材の採用と定着が最大の難所 |
| 外部委託（**MSS**） | 監視だけ外部に出す | 中堅以上 | 「アラートを転送されるだけ」だと現場が回らない |
| **MDR** | 監視＋**対応まで**外部が行う | 中堅・中小 | 端末隔離まで委託できる。範囲の線引きを契約で詰める必要 |
| **CSIRT** | 自社の**司令塔**。平時は訓練、有事は指揮 | 全組織（規模に応じた形で） | 監視の外注はできても、**意思決定は外注できない** |

**CSIRT**＝Computer Security Incident Response Team。
「事故が起きたときに誰が何を決めるか」をあらかじめ決めておく組織のこと。
専任部署でなくてもよく、兼務の指名でも成立する。重要なのは**連絡網と権限**。

## 5. インシデント対応の流れ：時計との戦い

事故が起きてからの動きは、業界でおおむね次の6段に整理される（NIST SP 800-61 の考え方が下敷き）。

```
 ①準備        ②検知・分析     ③封じ込め     ④根絶        ⑤復旧        ⑥教訓
 (Prepare)   (Detect)       (Contain)    (Eradicate)  (Recover)    (Lessons)
 ──────────────────────────────────────────────────────────────────────────
 体制/連絡網   何が起きたか    広がりを      原因を        業務を        再発防止と
 訓練/契約     どこまで侵入    止める        取り除く      戻す          開示・報告
 バックアップ  情報の持出有無  ネット遮断    穴を塞ぐ      段階的に      規制当局対応
 ──────────────────────────────────────────────────────────────────────────
   平時           数時間〜数日     数時間      数日〜数週    数週〜数ヶ月   数ヶ月
      ↑ ここでの準備量が、右側の全所要時間を決める
```

実務で必ず詰まるのは次の3点。

1. **止めるか、動かし続けるか**：ネットワークを切れば被害は止まるが業務も止まる。
   この判断は技術ではなく**経営判断**で、事前に基準を決めていないと初動で数日溶ける。
2. **何が漏れたかの特定**：ログが残っていなければ「分からない」としか言えない。
   分からないと**最大件数で開示するしかなくなり**、被害の見え方が膨らむ。
3. **復旧の順番**：全部同時には戻せない。どの業務から戻すかを事前に決めておく（BCPの領域）。

### 実際の所要時間の感覚

2025年の国内の大型事例では、**受注・出荷の停止が約2ヶ月に及んだケース**が報じられている
（アサヒグループホールディングス、2025年9月末発生／完全復旧は2026年）。
EC・物流のように**1日止まると日商がそのまま飛ぶ業態**では、
停止1日あたり10億円規模の機会損失という推計も出ている（アスクルの事例、報道ベース）。

> ポイント：セキュリティ投資の是非は「事故の確率×被害額」で語られがちだが、
> 実務的には**「止まったとき、1日いくら失うか」を先に出す**ほうが話が早い。
> この数字が出ると、どこまで投資するかが自動的に決まる。

## 6. 投資の優先順位：基本が効く

派手な製品より、地味な基本のほうが被害率を下げる。IPAの「情報セキュリティ10大脅威 2026」
解説書も、副題に「当たり前を確実に、基本の徹底と継続的な見直しで被害の最小化を」を掲げている。

| 優先度 | 打ち手 | なぜ効くか | コスト感 |
| --- | --- | --- | --- |
| 1 | **MFAの全面適用**（特にVPN・管理者・クラウド） | 盗まれた認証情報だけでは入れなくなる。IABの商品を無効化する | 低 |
| 2 | **インターネットに面した機器の更新** | 侵入経路の最上位。更新が止まった装置は「開いた窓」 | 低〜中 |
| 3 | **オフライン／改変不能バックアップ**と復旧訓練 | 払わずに戻せる。復旧訓練をしていないバックアップは無いのと同じ | 中 |
| 4 | **特権IDの管理（PAM）とネットワーク分離** | 入られても横に広がれない。被害範囲を1区画に閉じる | 中 |
| 5 | **EDR＋監視体制（SOC/MDR）** | 潜伏期間を短くする。窃取型に効く | 中〜高 |
| 6 | **ログ設計とSIEM** | 事後に「何が漏れたか」を説明できる。開示の質が変わる | 高（ログ量次第） |
| 7 | 演習（机上訓練・実地訓練） | 初動の判断が速くなる。効果は地味だが確実 | 低〜中 |

1〜3を済ませずに5〜6を買う組織は少なくない。
理由は、1〜3が**運用の手間で、買えば終わりにならないから**である。

## 7. AIが両側に効く

2025〜2026年の変化として、防御側・攻撃側の双方にAIが入ってきた。

| 側 | AIの使われ方 | 現時点の評価 |
| --- | --- | --- |
| 攻撃 | フィッシング文面の自然化・多言語化、偵察の自動化、攻撃コードの生成支援 | **量と速度**が上がった。CrowdStrikeはAI活用攻撃が2025年に前年比89%増と報告 |
| 攻撃 | 攻撃者自身がAIエージェントに一連の作業を任せる | 2026年の予測テーマ。トレンドマイクロ等が警戒を表明 |
| 防御 | アラートの一次分類、ログの自然言語照会、対応手順の下書き | SOCの人手不足を埋める方向で実装が進む |
| 新しい守備対象 | 自社が使うAI・AIエージェント自体（権限を持つ非人間ID＝NHI） | IPA「10大脅威 2026」で**AIの利用をめぐるサイバーリスクが初の3位** |

**NHI**（Non-Human Identity）＝人ではない主体のID。APIキーやサービスアカウント、
そしてAIエージェントが該当する。人よりはるかに多く、**退職も異動もしないので放置されやすい**。
従来のID管理が「人」を前提に作られてきたため、ここに空白がある。

詳細は [生成AI](../01_生成AI/README.md) と [05_直近トピック_2026](05_直近トピック_2026.md) を参照。

## 用語メモ

- **境界防御（ペリメータ）**：社内と社外を壁で分け、内側は信用する従来型の設計
- **ゼロトラスト**：社内外で区別せず、アクセスのたびに検証する設計思想。製品名ではない
- **ラテラルムーブメント（横移動）**：侵入後、社内の別のサーバーや端末へ広がる動き
- **EPP / EDR / NDR / XDR**：端末の防御／端末の検知と対応／通信の検知と対応／それらの統合
- **SIEM**：各種ログを1ヶ所に集めて突き合わせ、異常を見つける基盤
- **SOAR**：検知後の定型対応を自動化する仕組み
- **SOC**：監視を担う組織。**MSS**（監視のみ外注）と**MDR**（対応まで外注）がある
- **CSIRT**：事故対応の司令塔。平時の準備と有事の指揮を担う
- **PAM**：特権ID管理。管理者権限の貸し出しと記録を厳格にする
- **CSPM**：クラウドの設定ミスを点検する仕組み
- **DLP**：データの持ち出しを検知・制限する仕組み
- **NHI**：人以外のID（APIキー、サービスアカウント、AIエージェント）
- **NIST SP 800-61**：米国NISTによるインシデント対応の手引き。国内でも事実上の下敷き
- **MTTD / MTTR**：検知までの平均時間／復旧までの平均時間。SOCの成績表にあたる指標
