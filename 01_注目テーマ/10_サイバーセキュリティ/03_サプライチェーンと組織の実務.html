サプライチェーン攻撃と組織の実務（取引先・脆弱性管理・SBOM・人材）

このノートで分かること：自社をどれだけ固めても、
取引先・委託先・使っているソフトの部品から入られる構造がなぜ生まれるのか。
そして、それを管理しようとしたときに現場で何が起きるのか。

攻撃側の構造は 01_攻撃側の経済学、
防御の道具立ては 02_防御の全体像 を先に読むと理解が早い。

1. 結論：守る対象が「自社」から「つながり全体」に広がった

IPA「情報セキュリティ10大脅威 2026」（組織編）で、
第1位はランサム攻撃、第2位はサプライチェーンや委託先を狙った攻撃であり、
この2つは前年から順位が変わっていない。つまり構造的な問題として固定化した。

なぜ固定化したのか。攻撃側から見ると経済合理性があるからである。

    ┌─────────────────────────────────────────────┐
    │ 大企業A（守りが厚い。専任チーム、SOC、予算あり） │
    └──────▲──────────▲──────────▲───────────────┘
           │          │          │
    ┌──────┴───┐ ┌────┴─────┐ ┌──┴──────────┐
    │ 部品メーカーB│ │ 委託先C   │ │ 使っている  │
    │ 従業員80名 │ │ BPO/SaaS │ │ ソフトの部品 │
    │ 情シス1名  │ │          │ │ （OSS等）   │
    └──────────┘ └──────────┘ └─────────────┘
        ↑ ここを1回破ると、Aへの「正規の通路」が手に入る

同じ「Aへの侵入」を買うなら、守りの薄いところ経由のほうが安い。
01 で見たIAB（初期アクセスブローカー）の価格競争が、
この選択を後押ししている。

2. サプライチェーン攻撃は3種類ある

同じ言葉で呼ばれるが、対策が全く違うので分けて理解する。

類型 どこから来るか 代表的な被害の出方 効く対策
① 取引先・委託先経由（ビジネス型）業務でつながっている会社、BPO、データ処理の委託先委託先が止まって自社の業務も止まる。預けた個人情報が漏れる委託先の選定・監査、契約条項、預けるデータの最小化
② ソフトウェア／部品経由（技術型）使っているソフトの部品（OSS等）、更新の配信経路正規のアップデートに紛れて入ってくる。全ユーザーが一斉に影響SBOM、脆弱性管理、更新経路の検証
③ サービス／基盤経由SaaS、クラウド、ID基盤、MSP（運用受託業者）1社が破られると顧客企業が横並びで影響権限の最小化、ログの取得、代替手段の確保

日本で件数として目立つのは①で、2026年の公表事例でも
業務委託先へのランサムウェア攻撃から最大約19万件の個人情報が影響を受けた例が報じられている
（東海大学の事例、2026年）。委託先の情報でも、責任は委託した側にも残る。

③では、採用管理SaaSが内部で使っていたデータ分析ツールの脆弱性を突かれ、
マイナンバーや口座情報を含むデータに影響した可能性が報じられた例がある（2026年）。
自社が契約していない「契約先の契約先」で起きるため、自社からは見えない。

ポイント：①は契約と業務設計の問題、②は技術と資産管理の問題、
③は見えない依存の問題。ひとまとめに「サプライチェーン対策」とすると、
どれも中途半端になる。

3. 脆弱性管理：終わらない作業をどう終わらせるか

脆弱性＝ソフトウェアの欠陥のうち、悪用されると侵入や情報取得につながるもの。
毎年3万件規模で新たに公表され（CVE登録ベース）、数は増え続けている。
全部を直すのは物理的に無理なので、優先順位の付け方が実務の中身になる。

  ① 資産を把握する ──▶ ② 脆弱性情報を突き合わせる ──▶ ③ 優先順位を付ける ──▶ ④ 直す／緩和する
      何が            公表された欠陥と            危険度 × 露出度 ×       更新、設定変更、
      どこに          自社の資産を照合             悪用の実績             遮断、機器の撤去
      いくつあるか
      ↑ここが最難関                                         ↑ここが判断の中身

①の資産把握が最大の壁である。「使っているものを全部言えますか」に答えられる組織は少ない。
放置されたVPN機器、退職者が立てたサーバー、部署が勝手に契約したSaaS。
知らない資産は守れないし、更新もされないので、そこが侵入口になる。

優先順位を付けるときの軸は3つ。

軸 見るもの 実務での使い方
深刻度CVSSスコア（0〜10の共通指標）目安にはなるが、これだけで決めると量が多すぎて回らない
悪用実績KEV（米CISAの「実際に悪用された脆弱性」リスト）ここに載ったものは最優先。理論上の危険ではなく現実の危険
露出度インターネットに面しているか、認証の有無同じ欠陥でも、社内限定と全世界公開では危険度が桁違い

実務の合言葉は「インターネットに面していて、KEVに載っていて、認証なしで悪用できるもの」。
この3条件が揃ったものから直す。それ以外は計画的にやる。

4. SBOM：ソフトの「原材料表示」

SBOM＝Software Bill of Materials（ソフトウェア部品表）。
食品の原材料表示と同じで、そのソフトが何の部品でできているかの一覧である。

なぜ必要になったか。現代のソフトウェアは、自社で書いたコードが1〜2割、
残りはオープンソースの部品（OSS）を組み合わせたものという構成が普通になった。
そのため、ある部品に重大な欠陥が見つかったとき、

  • SBOMがない：「うちの製品に入っているか？」を全部調べ直す（数週間〜数ヶ月）
  • SBOMがある：一覧を検索して即座に影響範囲が出る（数分〜数時間）

という差が出る。2021年のLog4j（広く使われていたログ出力部品）の騒動で、
多くの組織が前者の状態にあることが露呈したのが、普及の直接の引き金になった。

論点 現状（2026年時点）
形式SPDX、CycloneDX の2系統が事実上の標準
制度EUサイバーレジリエンス法（CRA）が機械可読なSBOMを義務化。主要要件の適用は2027年12月から。ただし一般公開までは求めていない
日本経済産業省が「ソフトウェア管理に向けたSBOM導入に関する手引」を公表し、医療機器・自動車から先行
実務の壁作るのは自動化できるが、維持と、サプライヤーから集めることが難しい。部品の部品（推移的依存）まで追うと量が爆発する
誤解「SBOMがあれば安全になる」わけではない。在庫リストであって、鍵ではない

ポイント：SBOMの価値は「事故が起きてからの調べる速度」に出る。
平時には効果が見えないので、投資の説明がしにくいという構造的な弱点がある。

5. 取引先をどう管理するか：理想と現実

大企業が取引先に求める要求は年々増えている。一方で、要求される側の実力は追いつかない。

求める側（発注元）がやること 現場で起きる摩擦
セキュリティチェックシートを送る（数十〜数百項目）取引先は毎年何十社分の別々の様式に答えることになり、形骸化する
契約にインシデント報告義務・監査権を入れる中小の取引先には対応する人がいない。判子だけ押される
第三者認証（ISMS／ISO 27001、SOC 2）を要求する認証の取得費用が中小には重く、取引からの排除になりうる
実地監査・ペネトレーションテストを課すコストが大きく、全社には適用できない
預けるデータ自体を減らす最も確実だが、業務設計の見直しが要るので後回しになりやすい

現実的な着地点は、取引先をリスクで層別し、対応の重さを変えること。

  【層別の考え方】預けるデータの機微さ × 業務が止まったときの影響

   高 ┌──────────────┬──────────────┐
      │  重点管理      │  最重要         │
 機微 │ 定期監査＋契約  │ 実地監査・共同訓練│
 さ   ├──────────────┼──────────────┤
      │  通常管理      │  可用性重視      │
   低 │ チェックシート  │ 代替手段の確保    │
      └──────────────┴──────────────┘
        低          止まったときの影響          高

全社に最重要レベルを課すと、コストが見合わないうえに現場が回らない。
どこを重く見るかを決めること自体が、この領域の実務である。

6. 人材不足：数が足りないのではなく、配置が偏っている

セキュリティ人材不足はどの調査でも指摘されるが、内訳を見ると問題の形が違う。

不足している役割 何をする人か なぜ足りないか
監視・分析（SOCアナリスト）アラートを見て判断する24時間体制が要る。夜勤があり定着しにくい
インシデント対応（IR）事故のときに調べて止める経験がものを言う。経験は事故でしか積めない
マネジメント（CISO／企画）予算と優先順位を決め、経営に説明する技術と経営の両方が要る。最も希少
現場のセキュリティ担当（兼務）中小企業の情シス兼任そもそも専任枠がない

日本の制度的な手当てとしては、国家資格「情報処理安全確保支援士（RISS）」があり、
経済産業省は登録者を2030年までに約2.4万人から5万人へ増やす目標を掲げている。
ただし数を増やしても、中小企業に配置されなければ届かないという構造の問題が残る。

中小企業側の現実的な解は、抱え込まずに外に出すこと。

  • 監視はMDR（監視＋対応の外部委託）に出す → 02_防御の全体像
  • 事故対応は事前に契約しておく（起きてから探すと着手まで数日かかる）
  • 判断だけは内部に残す（CSIRTの指名。兼務でよい）
  • IPAの「SECURITY ACTION」など、やることを絞った公的な枠組みから始める

ポイント：人材不足を「採用で解決する」と考えると詰む。
外部に出せるもの（監視・調査）と、出せないもの（判断・説明責任）を分けるのが先。

7. 経営側から見たときの費用の話

セキュリティは売上を生まないので、投資の説明が構造的に難しい。
実務で使われている説明の型は3つ。

説明の型 中身 効きやすい相手
損失回避型「1日止まると◯億円。2ヶ月止まった事例がある」経営層（数字で話せる）
取引条件型「この認証がないと、この取引先から外される」事業部門（売上に直結する）
規制対応型「報告義務・課徴金がある」法務・管理部門 → 04_規制と制度

2020年代後半に取引条件型の圧力が強まったのが最大の変化である。
EUのNIS2やCRAは、対象企業だけでなくその取引先にも要求が波及する設計になっており、
「規制対象でない日本の部品メーカーが、欧州の顧客から要求される」という経路ができた。

用語メモ

  • サプライチェーン攻撃：取引先・委託先・ソフト部品・サービス基盤を経由して本命に侵入する攻撃の総称
  • 脆弱性：悪用されると侵入や情報取得につながるソフトウェアの欠陥
  • CVE：脆弱性に付けられる世界共通の識別番号
  • CVSS：脆弱性の深刻度を0〜10で示す共通指標。目安であって優先順位そのものではない
  • KEV：米CISAが公開する「実際に悪用が確認された脆弱性」のリスト。優先対応の実務基準
  • SBOM：ソフトウェア部品表。何の部品でできているかの一覧。形式はSPDXとCycloneDXが主流
  • OSS：オープンソースソフトウェア。現代のソフトの大半を占める部品
  • 推移的依存：部品が使っている部品。SBOMの量が爆発する原因
  • ISMS / ISO 27001：情報セキュリティマネジメントの第三者認証。取引条件として使われる
  • SOC 2：米国で広く使われる、サービス提供者向けの内部統制の報告基準。ISMSとは別系統
  • MSP：システム運用を受託する事業者。顧客横断の権限を持つため、破られると被害が広がる
  • RISS（情報処理安全確保支援士）：日本のセキュリティ分野の国家資格
  • SECURITY ACTION：IPAによる中小企業向けの自己宣言制度。最初の一歩として使われる
  • CISO：Chief Information Security Officer。セキュリティの最終責任者
