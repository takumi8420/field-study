# 日本のIT産業の構造 ── なぜエンジニアはベンダー側にいるのか

このノートで分かること：日本のITエンジニアの**約7割がユーザー企業ではなくベンダー（SIer・IT企業）に所属している**という
日米の決定的な差がどこから来たのか、そこから生まれた多重下請け構造の仕組み、
そして「批判されつつも半世紀続いてきた」のはなぜかという合理性の側面。

## 1. まず結論：この業界は「IT業」ではなく「人を貸す業」に近い

日本のSIer（システムインテグレーター）を理解する最短の道は、
**ソフトウェア会社だと思わないこと**である。売っているのは製品ではなく、**技術者の稼働時間**である。

```
  【米国型】                          【日本型】
  ユーザー企業                        ユーザー企業
  ┌──────────────┐                  ┌──────────────┐
  │ 社内エンジニア │ ← 主戦力        │ 情報システム部 │ ← 発注と管理だけ
  │  数百〜数千人  │                  │   数人〜数十人 │
  └──────────────┘                  └───────┬──────┘
        ▲                                    │ 発注
        │ 採用                               ▼
   労働市場（転職が普通）            ┌──────────────┐
                                     │  元請けSIer   │ ← エンジニアはここ
                                     └───────┬──────┘
                                             │ 外注
                                     ┌───────▼──────┐
                                     │  2次・3次請け  │
                                     └──────────────┘
```

> ポイント：**同じ「エンジニア」でも、日本では雇い主がユーザー企業ではなくベンダーである**。
> この1点から、人月商売・多重下請け・内製化の遅れ・クラウド移行の鈍さまで、ほぼ全部が説明できる。

## 2. 数字で見る日米差

| 国       | IT人材のうち**IT産業（ベンダー側）**に所属 | **非IT産業（ユーザー企業側）**に所属 |
| -------- | ------------------------------------------ | ------------------------------------ |
| 日本     | **72.3%**                                  | 27.7%                                |
| 米国     | 35.5%                                      | **64.5%**                            |
| ドイツ   | 38.6%                                      | 61.4%                                |
| 英国     | 約46%                                      | 約53%                                |
| フランス | 約46%                                      | 約53%                                |

出典：総務省『平成30年版 情報通信白書』（IPA『IT人材白書2017』を基に作成）。
2026年時点でもこの比率が劇的に変わったという統計はない（内製化の進展は後述→[変化と論点](04_変化と論点.md)）。

- 日本と米国で**ほぼ逆転している**。これは程度問題ではなく構造の違い
- 「日本にエンジニアが少ない」のではない。**所属先が偏っている**
- ユーザー企業に技術者がいないので、**要件を自分で書けない → 丸投げする → さらに技術が溜まらない**という循環になる

## 3. なぜこうなったのか（4つの歴史的要因）

### (1) メインフレーム時代のベンダー丸抱え（1960〜80年代）

コンピュータが1台数億円だった時代、ハード・OS・業務ソフト・運用・教育を**メーカーが一式で面倒を見た**。
富士通・NEC・日立はハードを売るために技術者を大量に抱え、顧客先に常駐させた。
ユーザー企業は「機械と一緒に技術者も付いてくる」ので、自社で抱える動機がなかった。

### (2) 雇用の硬直性 ── 需要変動を社内で吸収できない

日本の正社員は**景気が悪くなっても簡単には減らせない**（整理解雇の4要件など、判例上のハードルが高い）。
システム開発は、大型案件がある年とない年で必要人数が数倍変わる。

```
   必要な技術者数
    ▲
    │        ██                  ██
    │        ██      ██          ██        ← 大型更改・制度改正の年
    │   ██   ██  ██  ██   ██     ██   ██
    │   ██   ██  ██  ██   ██     ██   ██
    └────────────────────────────────────▶ 年
        ↑ ここを自社正社員で埋めると、谷の年に大量の余剰人員が出る
        ↑ だから「谷は自社、山は外注」で吸収する ＝ 多重下請けの経済的な理由
```

### (3) 情報子会社の切り出し

1980〜90年代、大企業は情報システム部門を**子会社として分社**した（いわゆるユーザー系SIer）。
理由は、給与体系を親会社と分けたかったこと、外販して収益化したかったこと、連結上の人件費管理。
結果として、ユーザー企業本体からエンジニアが**制度的に抜けた**。

### (4) 「作ること」を評価しない発注慣行

日本のユーザー企業では、情報システム部門は**コストセンター**として扱われ、
技術者としての昇進経路が細い。技術で認められたい人はベンダーへ行く。
ここは制度というより文化に近いが、人材の流れを長期に方向づけた。

## 4. ピラミッドの全体像

```
 【発注】 ユーザー企業（銀行・官公庁・製造業…）
              │  契約：一括請負が多い。金額は数億〜数千億
              ▼
 【1次】 元請けSIer（NTTデータ、富士通、NEC、日立、大手ユーザー系…）
         役割：要件定義・全体設計・品質保証・進捗管理・最終責任
              │  自社要員は2〜4割。残りは外注
              ▼
 【2次】 中堅SIer・協力会社（数百〜数千人規模）
         役割：サブシステム単位の設計・製造・テスト、要員の取りまとめ
              │
              ▼
 【3次】 小規模開発会社・SES専業（数十人規模）
         役割：詳細設計・コーディング・テスト実施
              │
              ▼
 【4次以下】 個人事業主（フリーランス）、一人社長の会社
```

| 階層    | 顧客との距離       | 主な契約形態      | 取り分（粗利のイメージ）                                             |
| ------- | ------------------ | ----------------- | -------------------------------------------------------------------- |
| 元請け  | 直接。経営層と会う | 一括請負／準委任  | 案件全体の利益を取る。下請け管理費も乗る                             |
| 2次     | 元請け経由         | 準委任（SES）中心 | 1人あたり月10〜20万円程度の差益が典型と言われる（推計）              |
| 3次     | ほぼ会わない       | 準委任（SES）     | 差益はさらに薄い                                                     |
| 4次以下 | 会わない           | 準委任／業務委託  | 単価は元請け提示額の半分以下になることもある（報道・実態調査ベース） |

公正取引委員会『ソフトウェア業の下請取引等に関する実態調査報告書』（2022年6月）は、
**商流に形式的に入るだけで何の業務もせず利益を得る「中抜き事業者」**の存在を明示的に問題として指摘した。

## 5. なぜ多重下請けは「合理的」に成立してきたのか

批判だけして終わると、この業界は理解できない。**続いてきたのには理由がある**。

| 機能                 | 誰にとっての合理性   | 中身                                                                     |
| -------------------- | -------------------- | ------------------------------------------------------------------------ |
| **需要変動の吸収**   | 元請け・ユーザー企業 | 案件の山谷を外部要員で埋める。自社雇用は谷に合わせて抑えられる           |
| **リスクの移転**     | ユーザー企業         | 一括請負にすれば、遅延・バグ・追加工数の責任は元請けが負う               |
| **与信の一元化**     | ユーザー企業         | 数百社に直接発注せず、1社に発注すれば支払・契約・責任が1本化する         |
| **人材の地理的動員** | 元請け               | 地方の開発会社まで含めて数千人を短期に集められる                         |
| **参入の容易さ**     | 下請け側             | 設備投資なしで、人を採って常駐させれば売上が立つ。開業資金がほぼ要らない |
| **雇用の受け皿**     | 社会全体             | 未経験者を採用して現場で育てる回路として機能してきた面がある             |

> ポイント：ユーザー企業は「自分で技術者を抱えるリスク」と「丸投げするコスト」を天秤にかけ、
> **長らく後者が安いと判断してきた**。多重下請けはその判断の帰結であって、誰かの悪意の産物ではない。

同時に、弊害も構造的である。

- **情報が伝わらない**：3次請けは顧客の業務を知らずに仕様書だけ見て作る → 手戻りが増える
- **単価が階層で削られる**：現場の技術者の待遇が上がらず、技術力が蓄積しない
- **責任の所在がぼやける**：障害時に誰が直すのかが契約上あいまい
- **偽装請負の温床**：請負契約なのに発注者が直接指揮命令すると違法（後述）

## 6. 契約形態の違い ── ここが最重要の実務知識

| 項目               | **一括請負**（請負契約）           | **準委任**（SES）                  | 派遣                           |
| ------------------ | ---------------------------------- | ---------------------------------- | ------------------------------ |
| 何を約束するか     | **成果物の完成**                   | **善良な管理者としての労務の提供** | 労働力の提供                   |
| 支払いの根拠       | 納品・検収                         | **稼働時間（人月）**               | 稼働時間                       |
| 瑕疵・不具合の責任 | 契約不適合責任を負う（請負人）     | 原則負わない（善管注意義務のみ）   | 負わない                       |
| 指揮命令           | **受注者が行う**。発注者は出せない | **受注者が行う**。発注者は出せない | **発注者が出せる**（派遣先）   |
| 必要な許認可       | なし                               | なし                               | **労働者派遣事業の許可が必要** |
| 発注側のリスク     | 高く見積もられる（リスク料込み）   | 工数が増えれば費用も増える         | 費用は増えるが人は選べる       |

**SES**＝System Engineering Service。法的には準委任契約で技術者を客先に出す商売のこと。
法律用語ではなく業界用語である。

**偽装請負**とは、契約は請負／準委任なのに、実態として発注者が受注者の技術者へ直接指示を出している状態。
労働者派遣法違反になる。多重下請けの現場では常に境界線上にあり、
「朝礼に出させる」「勤務時間を管理する」「直接作業指示をする」が典型的な危険サイン。

```
   一括請負：  発注者 ──[完成を約束]──▶ 元請け ──▶ 指揮命令 ──▶ 技術者
                （発注者は技術者に直接指示できない）

   準委任(SES)：発注者 ──[稼働を約束]──▶ ベンダー ──▶ 指揮命令 ──▶ 技術者
                （同上。指示はベンダーの責任者経由）

   派遣：      派遣先 ──[労働力の提供]──▶ 派遣元
                  └──────── 指揮命令 ────────▶ 技術者（これは合法）
```

## 7. 是正に向かう制度の流れ

| 時点       | 出来事                                                       | 意味                                                                     |
| ---------- | ------------------------------------------------------------ | ------------------------------------------------------------------------ |
| 2020年4月  | 改正民法施行（瑕疵担保責任 → **契約不適合責任**）            | 請負の責任範囲の整理                                                     |
| 2022年6月  | 公取委『ソフトウェア業の下請取引等に関する実態調査報告書』   | 中抜き事業者・買いたたきを名指しで指摘                                   |
| 2024年11月 | フリーランス・事業者間取引適正化等法（フリーランス新法）施行 | 個人への発注に書面明示・支払期日の義務                                   |
| 2026年1月  | 下請法改正 → **取適法（中小受託取引適正化法）**施行          | 手形払いの禁止、協議に応じない一方的な代金決定の禁止、従業員数基準の追加 |

取適法では資本金基準に加えて**従業員数基準（300人・100人）**が入り、
資本金を小さくして規制を逃れる形が塞がれた。手形払い禁止は資金繰りの弱い下請けに効く。
→ 直近の動きは [直近トピック_2026](05_直近トピック_2026.md)

## 8. 隣の業界との関係

- 人を貸して時間で稼ぐという点では [人材派遣](../../15_サービス・生活関連/01_人材派遣/README.md) と同型
- 業務そのものを引き受ける形は [アウトソーシング・BPO](../../15_サービス・生活関連/03_アウトソーシング・BPO/README.md)
- 上流（何を作るかを決める）に寄ると [コンサルティング](../../15_サービス・生活関連/04_コンサルティング/README.md) と競合する
- 作る対象がパッケージ／サブスクに置き換わると [ソフトウェア・SaaS](../06_ソフトウェア・SaaS/README.md)
- 載せる基盤が自社設備からクラウドへ移ると [クラウド・IaaS](../04_クラウド・IaaS/README.md)

## 用語メモ

| 用語                   | 意味                                                                                                |
| ---------------------- | --------------------------------------------------------------------------------------------------- |
| **SIer**               | System Integrator。複数のハード・ソフト・回線を組み合わせて業務システムを作り上げる事業者。和製英語 |
| **元請け（プライム）** | ユーザー企業と直接契約する立場。全体責任を負う代わりに利益も大きい                                  |
| **SES**                | 準委任契約で技術者を客先に常駐させる商売。成果物ではなく稼働時間を売る                              |
| **一括請負**           | 成果物の完成を約束する契約。予算は固定なので、工数超過は受注側の損になる                            |
| **準委任**             | 労務の提供を約束する契約。完成責任を負わない代わりに、工数分だけ請求できる                          |
| **偽装請負**           | 請負・準委任の形式で実態は派遣。発注者が直接指揮命令すると該当し、派遣法違反となる                  |
| **中抜き事業者**       | 商流に形式的に入るだけで実務を行わず利益を得る事業者。公取委の2022年報告書での定義                  |
| **取適法**             | 2026年1月施行。下請法の改正版（中小受託取引適正化法）。手形払い禁止などを規定                       |
| **ユーザー系SIer**     | 事業会社の情報システム部門が分社してできたSIer。親会社の業務知識が資産                              |
| **情報システム部**     | ユーザー企業側でIT投資の企画・発注・管理を行う部門。日本では人数が少ないのが典型                    |
