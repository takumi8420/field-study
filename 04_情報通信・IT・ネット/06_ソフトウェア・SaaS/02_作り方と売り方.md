# 作り方と売り方 ─ SaaSを成立させる開発・組織・営業の実務

このノートで分かること：SaaSが**全顧客に同じソフトを使わせる前提**で作られていること、
その前提から「アジャイル開発」「カスタマーサクセス」「PLG」といった耳慣れない言葉がすべて導かれること。
そして日本市場でだけ、その前提が**カスタマイズ要求**という壁にぶつかる理由。

## 1. 出発点：マルチテナントという設計

**マルチテナント**＝1つのシステムを全顧客で共用し、データだけを論理的に区切って見せる方式。
賃貸マンションに例えれば、建物と設備は1棟で共有し、部屋の鍵だけが顧客ごとに違う状態。

```
【売り切りパッケージ】           【SaaS（マルチテナント）】

  A社  B社  C社                     A社  B社  C社
   │    │    │                       └──┬──┴──┘
  [A用][B用][C用]  ← 3本を個別に          [共通の1本のシステム]
  [サーバ][サーバ][サーバ]                  ├ A社のデータ領域
                                            ├ B社のデータ領域
  改修も更新も3回                           └ C社のデータ領域
  バージョンが分かれる
                                     改修は1回で全社に届く
                                     バージョンは常に1つ
```

ここからSaaSの経済的な性質がすべて出てくる。

| 設計上の選択 | 事業への効き方 |
| --- | --- |
| 1本を共用する | 顧客が増えても開発費は増えない＝**粗利率75〜85%**の源泉 |
| バージョンが1つ | 旧版の保守が不要。開発資源を新機能に集中できる |
| 更新が即時に全社へ届く | 週単位で改善できる。使われない機能はすぐ分かる |
| **個別カスタマイズができない** | 顧客ごとの要望を断るか、設定で吸収するしかない |
| 障害が全社に波及する | 可用性（止まらないこと）が契約上の義務になる（SLA） |

> ポイント：SaaSの高い粗利率は「ソフトだから」ではなく「**1本を全員で使い回しているから**」。
> カスタマイズを受けた瞬間に、この経済性は崩れる。これが日本市場の論点の根っこ（第7章）。

## 2. 開発の回し方 ── アジャイルと継続デリバリー

| 方式 | 進め方 | SaaSに合うか |
| --- | --- | --- |
| ウォーターフォール | 要件定義→設計→開発→テスト→納品を一方通行で進む | 合わない。納品がゴールで、その後の改善が想定されていない |
| **アジャイル** | 1〜2週間の短い周期で「作る→出す→反応を見る→直す」を繰り返す | 合う。売った後が出発点というSaaSの性質と一致 |
| **CI/CD**（継続的インテグレーション／継続的デリバリー） | コードの変更を自動でテストし、自動で本番に反映する仕組み | 必須。手作業のリリースでは週次更新に耐えられない |

**なぜアジャイルでなければならないのか**は道徳の問題ではなく算数の問題。
月次で解約されうる商売では、機能改善が半年遅れると、その半年ぶんの顧客が先に抜ける。
一方、売り切りなら納品後に何を直しても売上は変わらないので、そもそも急ぐ理由がない。

開発組織で使われる指標も変わる。「工数（人月）」ではなく、
**デプロイ頻度・変更のリードタイム・変更失敗率・復旧時間**（いわゆるDORA 4指標）で測るのが一般的。

## 3. 売り方の二系統 ── PLGとSLG

| | **PLG**（Product-Led Growth／プロダクト主導型成長） | **SLG**（Sales-Led Growth／セールス主導型成長） |
| --- | --- | --- |
| 最初の接点 | 本人が無料で使い始める | 営業が訪問・商談する |
| 意思決定者 | 現場の担当者 | 情報システム部門・経営層 |
| 単価 | 低い（月数百円〜数千円/人） | 高い（年数百万〜数億円） |
| CAC | 低い。ただし機能開発に金がかかる | 高い。営業人件費が主 |
| 契約までの期間 | 数分〜数日 | 3〜12ヵ月 |
| 向く製品 | 一人で価値が出るもの（チャット、メモ、デザイン、開発ツール） | 全社で使って初めて価値が出るもの（ERP、人事、基幹系） |
| 代表例 | Slack、Zoom、Notion、Figma、Canva | Salesforce、Workday、SAP、ServiceNow |

```
【PLG】 無料で試す ─▶ 個人が使う ─▶ チームに広がる ─▶ 管理機能が要る ─▶ 会社契約
        （営業は最後の「会社契約」の段階でだけ登場する）
          ▲ 火種は現場。下から上へ広がる

【SLG】 リード獲得 ─▶ 商談 ─▶ 提案・PoC ─▶ 稟議・契約 ─▶ 導入支援 ─▶ 利用
        （契約までに人が介在し続ける）
          ▲ 火種は経営・情シス。上から下へ配られる
```

実際には二択ではなく、**PLGで入り口を作り、一定規模を超えた顧客に営業が乗る**併用型が主流。
2020年代以降は「PLS（Product-Led Sales）」とも呼ばれ、製品の利用ログを見て営業をかける相手を選ぶ。

## 4. 分業の型 ── The Model と各職種

米Salesforceが体系化し、日本でも広く模倣された分業モデル。1人の営業が全部やるのをやめ、段階ごとに担当を分ける。

```
 マーケティング ─▶ インサイドセールス ─▶ フィールドセールス ─▶ カスタマーサクセス
  見込み客を集める   電話・メールで選別     商談・クロージング      定着・追加販売
  （リード獲得）     （アポ創出）           （受注）               （継続・拡張）
       │                 │                     │                      │
    獲得件数           商談化率              受注率・単価          解約率・NRR
       └──────── ここまでが CAC ────────┘      └──── ここが LTV を決める ────┘
```

| 職種 | 役割 | 何で評価されるか |
| --- | --- | --- |
| マーケティング | 広告・イベント・記事で見込み客を集める | 見込み客の件数と質 |
| インサイドセールス（SDR/BDR） | 見込み客に接触し、商談に値するか選別する | 商談創出数 |
| フィールドセールス（AE） | 提案し、契約を取る | 受注額、受注率 |
| **カスタマーサクセス（CS）** | 契約後に「使いこなす」状態まで伴走する | **解約率、NRR、利用率** |
| サポート | 問い合わせに答える（受け身） | 一次解決率、応答時間 |

**カスタマーサクセスがなぜ必要なのか**：SaaSは使われなければ解約される。
問い合わせを待つサポートと違い、CSは**利用ログを見て、使われていない顧客に自分から連絡する**。
「ログインが週1回に落ちた」「特定機能を使っていない」といった兆候が、解約の先行指標になるため。
→ 解約率とNRRの意味は [SaaSの経済学](01_SaaSの経済学.md)

## 5. ホリゾンタルSaaSとバーティカルSaaS

| | **ホリゾンタル**（水平型） | **バーティカル**（垂直型） |
| --- | --- | --- |
| 対象 | 業種を問わない共通業務 | 特定業界の固有業務 |
| 例（国内） | freee・マネーフォワード（会計）、SmartHR（人事労務）、Sansan（名刺・請求書） | アンドパッド（建設）、カケハシ（薬局）、atama plus（教育）、キャディ（製造） |
| 市場の広さ | 広い（全企業が対象） | 狭い（業界の事業者数が上限） |
| 競合 | 多い。外資も来る | 少ない。業界知識が壁になる |
| 解約率 | 高めになりやすい（乗り換え可能） | 低い（業務そのものが乗っている） |
| 単価の伸ばし方 | 席数・上位プラン | **決済・金融・受発注など周辺機能の内包** |
| 難所 | 差別化と価格競争 | 市場の天井（TAMの小ささ） |

バーティカルSaaSが単価を伸ばす典型手は、ソフト利用料だけで終わらせず、
**その業界のお金の流れ（決済・請求・融資）に入り込む**こと。ソフトの月額が数万円でも、
取引額の数%を取れれば売上は桁が変わる。→ [フィンテック・キャッシュレス](../13_フィンテック・キャッシュレス/README.md)

## 6. 価格の設計 ── 何を単位に課金するか

| 課金単位 | 仕組み | 長所 | 短所 |
| --- | --- | --- | --- |
| **シート（席）課金** | 利用者1人あたり月額 | 分かりやすい、予算を組みやすい | 使わない人のアカウントを削られる。AIエージェントが人を代替すると席が減る |
| 階層（プラン）課金 | 機能の束をプランで分ける | アップセルの階段を作れる | プラン設計を誤ると上位に上がらない |
| **従量課金** | 処理件数・保存量・API回数 | 使われるほど増え、価値と一致する | 売上が読みにくい。顧客も予算を組みにくい |
| **成果課金** | 解決した件数・成約件数など結果に対して課金 | 顧客の納得感が高い | 成果の定義と計測でもめる。原価割れリスク |
| ハイブリッド | 基本料＋従量 | 収益の安定と上振れを両立 | 請求・計測の実装が重い |

2026年時点の潮流は「シート課金の比率低下・ハイブリッドの急増」。
調査ではシート単独が1年で21%→15%に低下し、ハイブリッドが27%→41%に増えたと報告されている（2026年、調査会社推計）。
背景と具体例は [直近トピック_2026](04_直近トピック_2026.md)。

## 7. 日本市場の壁 ── カスタマイズ要求という商習慣

SaaSは「みんなが同じものを使う」ことで成り立つ。ところが日本の企業ソフト市場は、
長らく **「自社の業務に合わせてシステムを作らせる」** 発注文化で動いてきた。

```
【欧米で多い順序】                 【日本で多い順序】

  SaaSを選ぶ                        自社の業務手順を書き出す
     ↓                                 ↓
  SaaSに合わせて業務を変える        それに合うシステムを作らせる
     ↓                                 ↓
  設定の範囲で微調整                SaaSを入れる場合も「うちの業務に合わせて」と要求
                                       ↓
  → 1本を全員で共用できる           → 個別対応が積み上がり、共用の前提が崩れる
```

| 要求の型 | SaaS事業者側で起きること | 現実的な対処 |
| --- | --- | --- |
| 画面・帳票の個別変更 | 分岐が増え、保守費が顧客ごとに発生 | 設定項目・テンプレートとして共通機能化する |
| 独自の承認フロー | ワークフロー機能の肥大化 | 汎用ワークフローとして作り込む |
| 既存基幹システムとの接続 | 個別の連携開発 | API公開＋連携パートナー（SIer）に任せる |
| オンプレ設置・専用環境の要求 | マルチテナントの否定 | 専用テナント版を高価格で用意するか、断る |
| 大幅値引きと年度末一括契約 | 収益認識と予測の乱れ | 定価運用と年間契約の徹底 |

**外資SaaSが日本で苦戦する典型パターン**も、機能不足より「本国がカスタマイズを許さない」ことによる。
逆に国産SaaSは、日本の制度（消費税・インボイス・電子帳簿保存法・社会保険・労基法）に密着することで戦う。
制度対応は毎年発生するため、**規制が国産SaaSの参入障壁になっている**面がある。

SIerとの関係は競合であり協業でもある。
導入設計・データ移行・周辺連携はSIerが担い、SaaS事業者は本体を作る、という分担が定着しつつある。
→ [SIer・ITサービス](../05_SIer・ITサービス/README.md)、[市場の構造](03_市場の構造.md)

## 8. 運用上の義務 ── SLAとセキュリティ

売り切りと違い、SaaSは**動かし続けること自体が商品**なので、次が契約上の義務になる。

- **SLA**（Service Level Agreement）：稼働率の保証。99.9%なら月あたり停止許容は約43分。下回れば返金・減額
- データの所在と管理：どの国のサーバに置くか（データ主権）、退去時の返却方法
- 第三者認証：ISMS（ISO/IEC 27001）、SOC 2、日本の政府調達では **ISMAP**（政府情報システムのためのセキュリティ評価制度）
- 権限管理：SSO（シングルサインオン）、SCIM（アカウントの自動連携）。大企業案件では必須要件になりやすい

→ 詳しくは [情報セキュリティ](../14_情報セキュリティ/README.md)、[サイバーセキュリティ](../../01_注目テーマ/10_サイバーセキュリティ/README.md)

## 用語メモ

| 用語 | 意味 |
| --- | --- |
| **マルチテナント** | 1つのシステムを全顧客で共用し、データだけを区切る方式 |
| **シングルテナント** | 顧客ごとに環境を分ける方式。要求に応えやすいが原価が上がる |
| **アジャイル開発** | 短い周期で作って出して直すを繰り返す開発の進め方 |
| **CI/CD** | 変更の検証と本番反映を自動化する仕組み |
| **PLG** | 製品そのものに顧客を増やさせる売り方。無料利用が入り口 |
| **SLG** | 営業が顧客を増やす売り方。高単価・長期商談 |
| **The Model** | マーケ→インサイドセールス→フィールドセールス→CSの分業型 |
| **インサイドセールス（SDR）** | 訪問せず電話・メールで見込み客を選別する職種 |
| **カスタマーサクセス** | 契約後の定着と拡張を担う職種。解約率とNRRで評価される |
| **オンボーディング** | 契約直後に使える状態まで立ち上げる工程 |
| **ホリゾンタルSaaS** | 業種を問わない共通業務向けのSaaS |
| **バーティカルSaaS** | 特定業界の固有業務に特化したSaaS |
| **シート課金** | 利用者数に応じた課金 |
| **従量課金** | 処理量・回数に応じた課金 |
| **成果課金** | 得られた結果の件数に応じた課金 |
| **SLA** | 稼働率などのサービス水準を保証する契約条項 |
| **ISMAP** | 政府調達向けのクラウドサービス安全性評価制度 |
| **SSO / SCIM** | 認証の統合／アカウント情報の自動連携の仕組み |
