# 市場の構造 ─ 誰が、どの業務領域で、何を売っているか

このノートで分かること：ソフトウェア産業が**パッケージ売り切りからSaaSへ移った経緯**、
業務領域ごとの主要プレイヤー、日本市場だけに存在する**SIerとの二層構造**、
そして2026年最大の論点である「**生成AIはSaaSを陳腐化させるのか**」の整理。

## 1. 産業の階層 ── SaaSはどこに座っているか

```
  ⑥ 利用企業・利用者                        全産業
  ─────────────────────────────────────────────
  ⑤ SaaS／業務アプリ      ★このノートの対象★   Salesforce, SAP, freee, SmartHR …
  ─────────────────────────────────────────────
  ④ 基盤モデル・AI API                       OpenAI, Anthropic, Google …
  ─────────────────────────────────────────────
  ③ クラウド（IaaS/PaaS）                    AWS, Azure, Google Cloud
  ─────────────────────────────────────────────
  ② データセンター                            NTT, Equinix, Digital Realty …
  ─────────────────────────────────────────────
  ① 半導体・サーバ                            NVIDIA, TSMC …

   ◀── 利益率が高いのは⑤（粗利75〜85%）。ただし2026年は④が⑤を侵食しうるかが論点
   ── 横から支える層：SIer（導入・連携・運用）、コンサル（業務設計）
```

- 下の層（①〜③）は設備投資型で、規模と資本が勝負 → [データセンター](../03_データセンター/README.md)、[クラウド・IaaS](../04_クラウド・IaaS/README.md)
- ⑤のSaaSは設備を持たず、**ソフトと顧客基盤が資産**。だから利益率が高く、参入も比較的容易
- ④の基盤モデルが業務ロジックを飲み込めば、⑤の存在意義が問われる（第7章）

## 2. パッケージからSaaSへ ── 何がこの移行を可能にしたか

| 時期 | 主流の形 | 背景 |
| --- | --- | --- |
| 〜1990年代 | メインフレーム・自社開発 | 大企業しかソフトを持てない |
| 1990〜2000年代 | **パッケージソフト売り切り**＋年間保守料（通常は定価の15〜20%） | CD-ROM／サーバ設置。ERPの普及 |
| 2000年代後半〜 | ASP／初期のSaaS | ブロードバンド普及。Salesforce（1999年創業）が先鞭 |
| 2010年代 | **SaaSが標準に** | クラウド（AWS等）の普及で、事業者側がサーバを持たずに済むようになった |
| 2020〜2022年 | コロナ禍で一気に拡大、評価も過熱 | リモートワーク需要。低金利が高成長株を押し上げた |
| 2023〜2025年 | 金利上昇で評価が調整、効率重視へ | 「成長一辺倒」から Rule of 40 へ |
| 2026年 | **AIによる代替懸念と課金モデルの再設計** | → [直近トピック_2026](04_直近トピック_2026.md) |

**移行を可能にした技術的な条件**は2つ。①常時接続のブロードバンドが当たり前になったこと、
②クラウドの登場でSaaS事業者自身がサーバ設備を持たずに済むようになったこと。
つまり **SaaSはクラウドの上に乗って初めて成立したビジネスモデル**であり、順番を逆にはできない。

売る側から見た移行の動機は、保守料の頭打ちにある。売り切りは新バージョンを買ってもらえないと
売上が伸びないが、SaaSなら毎月確実に入る。買う側の動機は、初期投資が要らないことと、常に最新版が使えること。

## 4. 業務領域別の地図

SaaSは「どの業務を置き換えるか」で分類すると理解しやすい。

```
 ┌──── バックオフィス ────┐ ┌─── フロントオフィス ───┐ ┌── 全社共通 ──┐
 │ 会計・経費・請求        │ │ 営業（CRM/SFA）        │ │ コミュニケーション │
 │ 人事・労務・給与        │ │ マーケティング（MA）   │ │ ストレージ・文書   │
 │ 法務・契約              │ │ カスタマーサポート     │ │ 認証・ID・セキュリティ │
 │ 調達・購買              │ │ EC・決済               │ │ 情報システム運用   │
 └─────────────────────────┘ └────────────────────────┘ └──────────────┘
           ▲ 制度対応が重く                 ▲ 成果が数字で見えやすく
             国産が強い領域                   外資が強い領域
```

| 業務領域 | 世界の主なプレイヤー | 国内の主なプレイヤー | 領域の性質 |
| --- | --- | --- | --- |
| 会計・経費・請求 | Intuit、SAP Concur、Bill | freee、マネーフォワード、ラクス（楽楽精算）、TOKIUM | 税制・インボイス・電子帳簿保存法への対応が必須。国産が強い |
| 人事・労務・給与 | Workday、SAP SuccessFactors | SmartHR、カオナビ、SAP系の日本版 | 社会保険・労基法に密着。国産が強い |
| 営業（CRM/SFA） | **Salesforce**、Microsoft Dynamics、HubSpot | Sansan、Mazrica、マツリカ系 | 外資が圧倒的。データが貯まるほど乗り換えにくい |
| コミュニケーション | Microsoft 365、Google Workspace、Slack、Zoom | Chatwork（kubell）、LINE WORKS | **束ね売り（バンドル）の主戦場**。単機能は飲み込まれやすい |
| 開発・IT運用 | GitHub、Atlassian、Datadog、ServiceNow | さくら系、国内ツールは少数 | 外資が強い。エンジニアが個人で選ぶためPLGが効く |
| セキュリティ | CrowdStrike、Okta、Zscaler | トレンドマイクロ、サイバーセキュリティクラウド | → [情報セキュリティ](../14_情報セキュリティ/README.md) |
| 業界特化（バーティカル） | Veeva（製薬）、Toast（飲食）、Procore（建設） | アンドパッド（建設）、カケハシ（薬局）、atama plus（教育）、キャディ（製造） | 業界知識が壁。解約率が低い |

## 5. 日本の構図 ── 「制度の壁」で守られた国産、機能で勝つ外資

| 観点 | 国産SaaS | 外資SaaS |
| --- | --- | --- |
| 強い領域 | 会計・人事・労務・請求（制度対応が必要な業務） | CRM、開発、IT運用、コミュニケーション |
| 強さの源 | 毎年の法改正に追随する開発力、日本語サポート、中小企業への営業網 | 機能の厚み、グローバル標準、資本力、既存の世界シェア |
| 弱点 | 海外展開が難しい（制度対応が国内限定の資産） | 日本固有の制度・商習慣への対応が遅い、カスタマイズを断る |
| 価格 | 中小企業でも払える水準 | 高い。大企業向け |
| 典型的な負け方 | 大企業案件で機能不足を突かれる | 中小企業市場に届かず、現場の運用に合わない |

**制度が参入障壁になっている**のが日本の特徴。インボイス制度（2023年開始）や電子帳簿保存法の改正のたびに
対応開発が必要で、これは日本市場だけのための投資になる。外資にとっては割に合わず、国産にとっては
「毎年必ず来る更新需要」になる。ただし裏返せば、**国産SaaSが海外で戦えない理由**でもある。

## 6. SIerとの関係 ── 競合であり、販路であり、補完でもある

日本には米国にない層がある。**SIer（システムインテグレーター）**＝顧客の要件に合わせてシステムを
設計・開発・運用する事業者。日本の企業ITは長くSIerへの一括発注で動いてきた。

```
【競合として】
  「SaaSを入れる」 vs 「SIerに作らせる」 ← 同じ予算を奪い合う
   標準機能に業務を合わせる    業務に合わせてシステムを作る

【販路として】
  SaaS事業者 ──製品──▶ SIer ──導入・設定・連携・教育──▶ 顧客企業
   自社では届かない大企業・地方企業へ、SIerの営業網で届く

【補完として】
  SaaS本体（標準機能）  ＋  SIerの作る「周辺」
                            ├ 既存基幹システムとのデータ連携
                            ├ 移行（旧システムのデータ投入）
                            ├ 業務設計・社内教育
                            └ 複数SaaSの統合運用
```

- SIerにとってSaaSは、当初は「売上を奪う敵」だった。1億円の受託開発が年数百万円のSaaS利用料に置き換わるため
- 現在は**SaaSの導入支援・連携開発で稼ぐ**方向に転換した企業が多い。粗利は受託より低いが、繰り返し受注できる
- 2026年の論点は、生成AIによるコード生成が**「作らせる」コストを下げてしまう**こと。
  既製品を買う理由が薄れれば、SaaSとSIerの綱引きの前提が変わる → [SIer・ITサービス](../05_SIer・ITサービス/README.md)

## 7. 生成AIはSaaSを陳腐化させるのか

2026年のこの業界で最大の論点。整理すると、懸念は**性質の違う3本**に分かれる。

| 懸念の種類 | 内容 | 効き方 |
| --- | --- | --- |
| ① **シート減少** | AIエージェントが人の仕事を代替すると、席数課金のSaaSは契約席数が減る | 売上に直接効く。NRRの主エンジンが折れる |
| ② **AIネイティブ競合** | AI前提で作られた新興企業が、既存SaaSより速く安く同じ業務を処理する | シェアを削られる。新興は短期でARR100億円規模に到達する例も |
| ③ **自作化（ビルド回帰）** | AIによるコード生成が進み、「買わずに作る」が現実的になる | 市場そのものが縮む可能性 |

これに対する反論も同じく3本ある。

| 反論 | 中身 |
| --- | --- |
| **データと業務が乗っている** | SaaSの価値はUIではなく、蓄積されたデータ・権限設計・監査ログ・法令対応。AIはそこを置き換えない |
| **AIは既存SaaSの武器にもなる** | 顧客データを持つ側がAIを載せる方が有利。課金を上乗せできる |
| **作るより運用が難しい** | 自作しても、可用性・セキュリティ・法改正対応・人員交代への耐性が要る |

Microsoftのサティア・ナデラCEOが2024年末の対談で
「ビジネスアプリケーションという概念は崩れる（業務ロジックはエージェント側に移る）」と述べたことが
この議論の口火になった（発言は報道・二次情報ベース）。
一方で調査会社IDCは、**2028年までに純粋なシート課金は陳腐化し、ソフトベンダーの約7割が価格戦略を
消費量・成果・組織能力といった新しい価値指標に組み替える**と予測している（IDC予測、推計）。

> 現時点で優勢な見方：「SaaSが死ぬ」のではなく「**SaaSの課金単位と競争軸が変わる**」。
> 席を売る商売から、処理した仕事量・出した成果を売る商売へ移行する、という整理。
> 具体的な2026年の動きは [直近トピック_2026](04_直近トピック_2026.md) を参照。

## 用語メモ

| 用語 | 意味 |
| --- | --- |
| **パッケージソフト** | 買い切って自社サーバに入れて使うソフト。年間保守料が別途かかる |
| **ERP** | 会計・人事・販売・在庫を1つに束ねた基幹システム |
| **CRM / SFA** | 顧客管理／営業支援のシステム |
| **MA** | マーケティングオートメーション。見込み客の育成を自動化する |
| **ITSM** | IT運用の問い合わせ・変更管理を扱う仕組み |
| **バンドル（束ね売り）** | 複数機能をまとめて売ること。単機能SaaSの最大の脅威 |
| **SIer** | 顧客の要件に合わせてシステムを設計・開発・運用する事業者 |
| **インボイス制度** | 2023年開始の消費税の仕入税額控除方式。請求書SaaSの需要源 |
| **電子帳簿保存法** | 帳簿書類の電子保存を定める法律。改正のたびに対応需要が出る |
| **AIネイティブ** | 最初から生成AIを前提に設計された製品・企業 |
| **エージェント** | 指示を受けて複数の手順を自律的に実行するAI |
| **TAM** | 狙える市場の最大規模。バーティカルSaaSの評価で必ず問われる |
