クラウドとは何を売っているか ── IaaS/PaaS/SaaSと従量課金

情報通信・IT・ネットクラウド・IaaS
あこのページの単語集用語に触れると意味を確認できます17語
可用性を買える遅延を買える法令対応を買えるIaaSPaaSSaaS従量課金CapEx / OpExリージョンAZ（アベイラビリティゾーン）マネージドサービスサーバレス責任共有モデルSLAロックインクラウドリパトリエーションハイパースケーラー

このノートで分かること：クラウド事業者が顧客に渡している「商品」の正体と、
それがオンプレミス（自社保有のサーバ）と何が決定的に違うのか。

1. 結論：売っているのは「サーバ」ではなく「待たなくていい権利」

クラウドの本質を一言でいうと、買えば数か月かかるものを、数分で借りられるようにしたこと。

自社でサーバを持つ場合、企画 → 見積 → 稟議 → 発注 → 納品 → ラック搭載 → OS設定と進み、
使えるようになるまで数週間から数か月かかる。しかもその台数は「ピーク需要」に合わせて買う。
クラウドでは同じことがAPIコール1回・数分で終わり、要らなくなれば止めた瞬間に課金が止まる。

ポイント：クラウドが売っているのは計算資源そのものではなく、
「調達のリードタイムをゼロにし、不要になったら返せる」という時間とオプションである。
値段が安いから使われているのではない（後述のとおり単価はむしろ高いことが多い）。

物理的な箱・電気・冷却の層は データセンター が担う。
このフォルダはその上に載るサービスと事業構造を扱う。

  半導体 ─▶ データセンター ─▶ ★クラウド／IaaS★ ─▶ 基盤モデル ─▶ SaaS ─▶ ユーザー企業
   GPU/CPU   電気・冷却・箱      計算資源とAPI        AIモデル     業務ソフト
                                       ▲
                       ここが「仮想化された資源をメニュー化して売る」層

2. IaaS / PaaS / SaaS ── どこまで預けるかの三段階

クラウドは「どこまで事業者にやってもらうか」で層が分かれる。この3語は難しく見えるが、
自分でやる仕事が上から順に減っていくだけである。

層 借りるもの 自分でやること 例 単価と粗利
IaaS（Infrastructure as a Service）仮想サーバ、ストレージ、ネットワークOS更新、ミドルウェア、アプリ、運用AWS EC2、Azure VM、Compute Engine単価は安い。粗利も薄め
PaaS（Platform as a Service）DB・実行環境・キューなど「動く部品」アプリと設定だけAWS RDS／Lambda、Azure SQL、BigQuery単価が上がる。粗利が厚い
SaaS（Software as a Service）完成した業務ソフトデータを入れて使うSalesforce、Microsoft 365ユーザー課金。別産業 → ソフトウェア・SaaS

「as a Service」は所有せず、使った分だけ料金を払う形で提供されるという意味。

  ┌──────────────┬──────────┬──────────┬──────────┐
  │ 作業          │ オンプレ  │  IaaS    │  PaaS    │
  ├──────────────┼──────────┼──────────┼──────────┤
  │ 建物・電気     │  自社     │ 事業者   │ 事業者   │
  │ サーバ調達     │  自社     │ 事業者   │ 事業者   │
  │ 仮想化         │  自社     │ 事業者   │ 事業者   │
  │ OS・パッチ     │  自社     │ ★自社★  │ 事業者   │
  │ ミドル(DB等)   │  自社     │ ★自社★  │ 事業者   │
  │ アプリ         │  自社     │  自社    │  自社    │
  │ データ         │  自社     │  自社    │  自社    │
  └──────────────┴──────────┴──────────┴──────────┘
        下から順に「自社」の欄が消えていくのがクラウド化

IaaSだけ使う顧客は、事業者にとって一番おいしくない顧客である。
安い仮想サーバを借りて中身は全部自分で作るので、他社へ移るのも比較的容易。
事業者が本当に売りたいのは次章以降で述べるマネージドサービス（PaaS層）になる。

3. 従量課金という発明 ── なぜこれが産業を変えたか

クラウド以前、計算資源は「台数 × 買い切り」でしか買えなかった。
クラウドは秒／GB／リクエスト単位の従量課金に置き換えた。これは価格表の話ではなく、
IT投資の意思決定そのものを変えた。

変わったこと 以前 クラウド以後
必要な資金先に数千万〜数億円初月は数万円から
決裁の重さ設備投資として取締役会級経費として現場判断
失敗コスト買った機械が残る止めれば終わり
容量設計ピークに合わせて過剰に買う必要な時だけ増やす
会計上の扱いCapEx（設備投資、資産計上して数年で償却）OpEx（経費、その期に費用化）

ポイント：「試して駄目なら捨てる」が経済的に成立するようになったことが本質。
スタートアップが少額で始められるようになった理由も、大企業が新規事業を量産できるようになった理由も、
技術ではなくこの課金方式にある。

ただし従量課金は上振れも自由である。設定ミスやコード不具合で請求が10倍になる事故（いわゆる「請求書ショック」）は
日常的に起きる。この裏返しとして生まれたのがコスト管理の専門職＝FinOpsで、
詳しくは 02_儲け方と経済性 で扱う。

4. リージョンとAZ ── 地理と可用性をメニュー化する

クラウドは世界をリージョン（Region）という単位に区切って売っている。

  • リージョン＝独立した地理的な区画。例：東京（ap-northeast-1）、大阪、バージニア北部
  • アベイラビリティゾーン（AZ）＝1リージョン内にある、電源も建物も分かれた複数のデータセンター群
        リージョン（例：東京）
   ┌──────────────────────────────────────┐
   │  AZ-a        AZ-c        AZ-d        │
   │ ┌─────┐    ┌─────┐    ┌─────┐        │   AZ同士は数km〜数十km離れ、
   │ │ DC  │    │ DC  │    │ DC  │        │   電源・回線が独立。
   │ │ DC  │    │ DC  │    │ DC  │        │   低遅延の専用回線で結ばれる
   │ └─────┘    └─────┘    └─────┘        │
   └──────────────────────────────────────┘
        ▲ 1つのAZが落ちてもサービスを続けられる設計が前提

なぜこの区切りが商売になるのか。

  1. 可用性を買える：2つ以上のAZにまたがって置けば、片方の停電・火災でも止まらない。
    自社でこれをやるには建物を2棟借りる必要がある
  2. 遅延を買える：利用者の近くのリージョンを選べば応答が速い
  3. 法令対応を買える：「データを日本国内から出さない」といった要件に、リージョン選択で応えられる
    → 主権の議論は 03_競争構造 の国産クラウド／ソブリンクラウドへ

同時に、リージョンは地政学リスクの単位でもある。どの国の法律が及ぶかはリージョンの所在地ではなく
事業者の本社所在国にも左右される（米国CLOUD Act等）ため、「日本リージョンだから国内法だけ」とは言い切れない。

5. マネージドサービスこそが本体の価値

仮想サーバを借りるだけなら、実はクラウドは割高なことが多い。
同じ性能のサーバを3年使うなら、自社で買ったほうが安いという試算は珍しくない。
それでも企業がクラウドを選ぶのは、「運用を丸ごと引き受けてくれる部品」が使えるからである。

マネージドサービスの例 自前でやると必要な仕事 事業者が肩代わりする内容
マネージドDB（RDS、Cloud SQL 等）バックアップ、フェイルオーバー、バージョン更新、専任DBAボタン1つで冗長構成・自動バックアップ
オブジェクトストレージ（S3 等）ストレージ装置の増設、多重化、故障交換容量無制限・11ナインの耐久性をうたう
サーバレス（Lambda、Cloud Run 等）サーバの台数設計と常時稼働リクエストが来た時だけ実行し、その分だけ課金
マネージドKubernetes制御基盤の構築と更新コントロールプレーンを事業者が運用
マネージドAI（Bedrock、Vertex AI 等）GPU調達、モデル配備APIを叩くだけでモデルが使える → 生成AI

ポイント：クラウドの競争は「CPUが速いか」ではなく、
「面倒な運用をどれだけメニュー化できたか」で決まる。
数百のサービスを並べられること自体が参入障壁になっている。

そしてマネージドサービスを深く使うほど、そのクラウド固有のAPIに依存する。
これがロックイン（囲い込み）の正体であり、事業者にとっては粗利の源泉でもある
（→ 02_儲け方と経済性）。

6. オンプレとの比較 ── CapExからOpExへ、そして「両方」へ

論点 オンプレミス（自社保有） クラウド
会計CapEx。資産計上し5年前後で償却OpEx。使った月の経費
初期費用大きいほぼゼロ
総額（安定稼働・長期）安くなりうる割高になりやすい
需要が読めない／季節変動過剰投資になる圧倒的に有利
調達リードタイム数週間〜数か月数分
人材インフラ運用の内製が必要アプリ側に人を寄せられる
障害時の責任全部自社責任共有（次章）
撤退機械が残る止めれば終わる（データ移送費は別）

この表から分かるのは、クラウドが常に正解ではないということ。
負荷が一定で24時間フル稼働するシステム（基幹バッチ、大規模推論の常時稼働など）は、
自社設備のほうが単位コストが低くなりやすい。

そのため2020年代後半は「全部クラウド」からハイブリッド（使い分け）へ実務が寄っている。
一部ワークロードを自社設備へ戻す動きはクラウドリパトリエーションと呼ばれ、
IDCの調査ではCIOの86%が一部の戻しを計画する一方、完全撤退の計画は約8%にとどまるとされる（2025年、報道ベース）。
つまり「クラウドをやめる」のではなく「置き場所を使い分ける」段階に入っている。

7. 責任共有モデル ── どこまでが事業者の仕事か

クラウド事故のニュースを読み解く鍵がこれ。事業者と顧客の責任範囲は契約上はっきり分かれている。

  ┌────────────────────────────────────────────┐
  │  顧客の責任（in the cloud）                  │
  │   データ、アクセス権限、暗号化設定、         │
  │   OS・ミドルの更新（IaaSの場合）、アプリ     │
  ├────────────────────────────────────────────┤
  │  事業者の責任（of the cloud）                │
  │   建物、電源、ハード、仮想化基盤、           │
  │   マネージドサービスの中身                   │
  └────────────────────────────────────────────┘

情報漏洩事故の多くは顧客側の設定ミス（ストレージを公開設定にしたまま等）で起きる。
一方で大規模障害は事業者側の設定変更やネットワーク不具合で起きる。
どちらの領域の話かを見分けると、報道の意味が正確に読める
（→ 情報セキュリティ）。

SLA（サービス品質保証）も理解しておきたい。多くのクラウドのSLAは
「守れなかったら料金の数%〜数十%を返す」という設計で、
顧客の逸失利益を補償するものではない。可用性の担保は最終的に顧客側の設計責任になる。
